# IrisArsenal 正式版2.0之后的优化计划

日期：2026-10-24。本文是实施方案，本次不修改战斗代码、不编译、不部署新DLL。正式版2.0保留内部0.4.34 / IRIS_MEDICAL_GATE_083。

## 已有依据与目标

重负载083日志的完整摘要id6/frame2589中，1321次原生受击累计378.5357ms，平均约0.287ms，最慢单次约7.857ms；该阶段约占damage_flush累计443.802ms的85.3%。日志按1ms阈值记录的88次慢调用只占约6.7%，但贡献约73%的原生受击时间。身份检查约2.562ms、伤害计算约8.481ms、经验阶段约1.738ms；因此只优化外围容器无法直接消除这个主要长尾。

这不是“1321次只耗7.857ms”：7.857ms是一笔原生受击的墙钟耗时。内部哪一环变慢尚未确认，墙钟也可能包含线程抢占、同步等待及其他插件重入，不能全部当成CPU执行时间。

伤害等待平均约60.27ms、最大902.61ms；397/1384个请求超过40ms。具体60请求队列案例分14批，实际Flush累计39.12ms，但相邻服务间隔约50～83ms，末尾等待约902.6ms。它同时包含慢调用和服务机会间隔，不等于原生持续计算了902.6ms。查询等待平均15.09ms、最大1134.38ms；不能据此删除查询安全门。

上述测试不是固定场景A/B，不能由日志换算FPS或保证下一轮提高多少帧。当前日志直方图按安全更新帧汇总，不能冒称原生单次调用p95/p99。后一次轻负载日志不作为同等负载性能提升证据。

## 第一轮具体交付范围

先实施第2～4项的最小可关闭诊断和固定测试记录，定位长尾并证明额外服务机会是否存在。第5、6、8、9项都必须满足表内前置证据后才改，不一次性将调度、原生医疗、碰撞缓存同时改掉。

保留当前2.5ms软预算、32次上限、FIFO；单次调用不可抢占，超过预算后停止取下一条，下一次从最老的剩余请求继续。无需给FIFO再套优先堆。不得靠把更多碰撞推迟到后面来宣称帧耗时改善。
